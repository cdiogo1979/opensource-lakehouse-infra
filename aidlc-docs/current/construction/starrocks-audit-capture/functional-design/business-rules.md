# Business Rules — StarRocks Audit Capture (U1, U2, U3)

Intent `20261125-starrocks-audit-capture`. One consolidated functional design for the three units (approved execution plan). Rules are numbered `AC-n`.

## U1 Capture
- **AC-1 Staging DDL**: `CREATE DATABASE IF NOT EXISTS starrocks_audit_db__`; `CREATE TABLE IF NOT EXISTS starrocks_audit_db__.starrocks_audit_tbl__` with the columns of [domain-entities.md](domain-entities.md), `ENGINE = OLAP`, `DUPLICATE KEY (queryId, timestamp, queryType)`, `PARTITION BY date_trunc('day', timestamp)`, `PROPERTIES ("replication_num" = "1", "partition_live_number" = "7")`.
- **AC-2 Existing table**: column names and types are compared with the expected list (case-insensitive names, normalized types). Extra columns are allowed (the plugin and readers match by name); missing or retyped columns are reported as a problem; the table is never altered or dropped by the bootstrap.
- **AC-3 Loader password**: 32 random URL-safe characters (`secrets.token_urlsafe`), written once to `.runtime/credentials/srv-auditloader-password` with mode 0600; reused on later starts; rotation = delete the file and run `start` (AC-8 reinstalls with the new password).
- **AC-4 Loader user**: `srv-auditloader` with the native password plugin. Created if missing; on every run `ALTER USER ... IDENTIFIED BY` sets the file's password (idempotent, keeps rotation simple); then `GRANT INSERT ON TABLE starrocks_audit_db__.starrocks_audit_tbl__ TO USER srv-auditloader`. It never gets any role. A user of that name with another login plugin (LDAP, JWT) is a conflict: reported, not changed.
- **AC-5 Package verification**: the lock file `infra/starrocks/plugins/auditloader.lock` (YAML: `version`, `file`, `source_url`, `sha256`, `license`) names the vendored package; its SHA-256 must equal the lock's before anything is rendered or installed. A mismatch stops the audit capture step: the bootstrap prints the error and continues (StarRocks and the rest of `start` keep running, nothing is installed), and `status` shows the plugin missing. The same applies to any other capture failure. (Refined at Code Generation, 2026-11-25.)
- **AC-6 `plugin.conf` rendering**: start from the vendored package's own `plugin.conf`; set exactly `frontend_host_port=127.0.0.1:8030`, `database=starrocks_audit_db__`, `table=starrocks_audit_tbl__`, `user=srv-auditloader`, `password=<file>`, `secret_key=` (empty); keep every other key and comment as shipped; a key missing from the template is appended. The password must not contain a newline or `=`-prefixed tricks: generated passwords are URL-safe, so this holds.
- **AC-7 Built package**: a zip with the vendored `auditloader.jar` and `plugin.properties` unchanged and the rendered `plugin.conf`, with fixed timestamps and order (deterministic bytes), written to `.runtime/starrocks-audit/auditloader.zip` (mode 0600, folder 0700). Its SHA-256 is the **package digest**.
- **AC-8 Install decision**: from `SHOW PLUGINS` and the digest recorded at the last install (`.runtime/starrocks-audit/installed.sha256`):
  - no `AuditLoader` plugin → `install`;
  - installed, status not `INSTALLED`, or recorded digest different from the new one → `reinstall` (`UNINSTALL PLUGIN AuditLoader`, then install);
  - installed with the same digest → `keep`.
  Install is `INSTALL PLUGIN FROM "/opt/lakehouse/starrocks-audit/auditloader.zip"` (a read-only bind mount of `.runtime/starrocks-audit/` into the FE); after a successful install the digest file is written.
- **AC-9 Persistence**: the FE's plugin folder `/opt/starrocks/fe/plugins` is a named volume (`starrocks-fe-plugins`) so a recreated FE container keeps the installed plugin that its metadata (`starrocks-fe-meta`) refers to; the package stays at its install path (AuditLoader's requirement).
- **AC-10 Login events**: `infra/starrocks/conf/fe.conf` sets `audit_log_modules = slow_query,query,connection`; staging rows then have `queryType` `query`, `slow_query`, `connection` or `disconnection`.
- **AC-11 Status**: `capture_status` reports the plugin state (`INSTALLED`, missing, or the StarRocks status text) and the age of the newest staging `timestamp` (or "no rows"); `scripts/lakehouse.sh status` prints one line; it fails no command.
- **AC-12 Order**: in `bootstrap-starrocks.py`, audit capture runs after the root password, the BE and the LDAP login, in both `--runtime-only` and full runs; in a full run it also runs before `ensure_roles` (AC-15 grants need the table). `--dry-run` prints the plan only. StarRocks disabled → skipped like the rest.

## U2 Product model and grants
- **AC-13 Schema**: optional top-level key `platform_sources`, a mapping whose only allowed key is `starrocks_audit`; its value maps each of `owner`, `developer`, `analyst`, `writer` to `none` or `read`; every role must be present when the source is given (explicit, like `access`). Unknown keys, roles or levels → `ProductError` naming the field.
- **AC-14 Default**: no `platform_sources` (or no `starrocks_audit`) means `none` for every role; existing product files stay valid and unchanged.
- **AC-15 Grant**: for each product role with `read`: `Grant(role, "SELECT", "default_catalog", "TABLE starrocks_audit_db__.starrocks_audit_tbl__")`, rendered `SET CATALOG default_catalog; GRANT SELECT ON TABLE starrocks_audit_db__.starrocks_audit_tbl__ TO ROLE <role>;`. `parse_role_grants` understands `TABLE <db>.<table>` objects, so the grant is seen as current (no re-grant, no "unrecognised" warning) and revoked when no longer declared (AC-14).
- **AC-16 Who may declare it**: any product file may, but the platform docs say it is meant for the audit product; `audit.yaml` declares owner, developer and writer `read`, analyst `none`.

## U3 Connection helper
- **AC-17 Mode**: `LAKEHOUSE_TOKEN_PROVIDER=airflow` → Airflow mode; `JUPYTERHUB_USER` set (and not Airflow) → Jupyter mode; otherwise `RuntimeError("lakehouse_starrocks.connect() works in an Airflow run or a JupyterHub server")`.
- **AC-18 Settings**: host `LAKEHOUSE_STARROCKS_HOST` (default `starrocks-fe`), port `LAKEHOUSE_STARROCKS_PORT` (default `9030`, integer 1–65535), CA `LAKEHOUSE_STARROCKS_CA` (must be an existing file); user: `LAKEHOUSE_STARROCKS_USER` in Airflow (required), `JUPYTERHUB_USER` in Jupyter. Any missing or invalid value → `RuntimeError` naming the variable, never its value if secret.
- **AC-19 Airflow token**: use `LAKEHOUSE_INITIAL_ACCESS_TOKEN` while its JWT `exp` is more than 120 seconds away (the payload is decoded without verification only to read `exp`; StarRocks verifies the token); otherwise `POST {LAKEHOUSE_TOKEN_BROKER_URL}/v1/runs/token` with `Authorization: Bearer {LAKEHOUSE_RUN_CAPABILITY}`, body `{"run_handle": LAKEHOUSE_RUN_HANDLE}`, TLS verified with `LAKEHOUSE_TOKEN_BROKER_CA`, timeout 10 s, response ≤ 8 KiB with a string `access_token`; the new token is kept in the process for later calls. Errors raise `RuntimeError` without the broker's body.
- **AC-20 Login**: Airflow: PyMySQL with the token as password and `auth_plugin_map={b"authentication_openid_connect_client": <OIDC handshake>}` (as `mv_deploy`); Jupyter: the password from `getpass.getpass("StarRocks password for <user>: ")`, used once, not stored. Both: `ssl` context with `cafile=` the CA and hostname checking on, `autocommit=True`, `connect_timeout=15`, `read_timeout=600`, `charset="utf8mb4"`.
- **AC-21 No secrets out**: the module never prints, logs or puts in an exception message a token, capability or password.
- **AC-22 Mounts and variables**: Airflow run containers: CA at `/run/certs/starrocks-ca.crt` (read-only) and `LAKEHOUSE_STARROCKS_HOST`, `_PORT`, `_CA`, `_USER` (the product's `writer_user.username`); Jupyter servers: the same CA path and `_HOST`, `_PORT`, `_CA` (no `_USER`: the user is the JupyterHub user). Host paths come from the existing environment conventions of each service.
- **AC-23 Lock**: `PyMySQL==<pinned>` in `infra/workload-python/requirements.in`; `requirements.lock` regenerated; pure-Python wheel (no aarch64 constraint).
