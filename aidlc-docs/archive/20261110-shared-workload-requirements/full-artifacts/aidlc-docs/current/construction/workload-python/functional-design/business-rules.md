# Business Rules — workload-python

## Lock (BR-L)
- **BR-L1**: Lines are `name==version`, comments (`#` at line start) or blank. Anything else is a problem naming the line.
- **BR-L2**: `name` matches `[A-Za-z0-9]([A-Za-z0-9._-]*[A-Za-z0-9])?`; `version` matches `[A-Za-z0-9.+!_-]+`.
- **BR-L3**: No normalized name appears twice.
- **BR-L4**: The lock never holds `pyspark`, `py4j`, `pip`, `setuptools` or `wheel` (platform-managed).
- **BR-L5**: The lock is not empty. It starts with the generator's header: `# Generated by scripts/setup/lock-workload-python.sh from requirements.in. Do not edit.`

## Environment check (BR-V), used by both image builds, the parity verifier and after installs
- **BR-V1**: The interpreter reports Python 3.10.
- **BR-V2**: `pip freeze` runs with `PYTHONPATH` and every `PIP_*` variable removed, so `/opt/spark/python` (which would list `pyspark`) and user settings don't affect it.
- **BR-V3**: Every locked package is installed at exactly the locked version; otherwise "missing" or "<name>: <installed> installed, <locked> locked".
- **BR-V4**: Without `--allow-extra`, any installed package not in the lock is a problem ("not in the lock"). With `--allow-extra` (after extras installs), additional packages are allowed and listed.
- **BR-V5**: Versions compare as exact text after normalizing names only.

## Extras file (BR-E)
- **BR-E1**: The file is UTF-8, at most 64 KiB, at most 200 requirement lines. Otherwise a single problem.
- **BR-E2**: Blank lines and comments are ignored: a line starting with `#`, or text from a `#` preceded by whitespace.
- **BR-E3**: Refused, with the reason "options are not allowed": any line starting with `-` (for example `-r`, `-c`, `-e`, `-i`, `--index-url`, `--extra-index-url`, `-f`, `--find-links`, `--hash`, `--pre`, `--trusted-host`).
- **BR-E4**: Refused, "URLs and paths are not allowed": a line containing `@` or `://`, or starting with `.`, `/` or `~`; also a line ending with `\` (continuation).
- **BR-E5**: An accepted line is `name`, optional `[extra, ...]`, optional comma-separated specifiers (`==`, `!=`, `<=`, `>=`, `<`, `>`, `~=` followed by a version), and an optional `; marker` (left to pip). Anything else: "not a plain requirement". `===` is refused.
- **BR-E6**: Refused, "provided by the platform": `pyspark` and `py4j` (they come from `/opt/spark`), and `pip`, `setuptools`, `wheel`.
- **BR-E7**: A name appearing twice is a problem.
- **BR-E8**: Listing a locked package is allowed. The lock is a constraint, so a different version fails resolution and the same version changes nothing.
- **BR-E9**: All problems of the file are reported together, each as `requirements.txt:<line>: <message>`.

## Resolution and installs (BR-R)
- **BR-R1**: Wheels only: every resolution and install passes `--only-binary=:all:` (Application Design Q1).
- **BR-R2**: The lock is always passed as `--constraint`; extras can never change a locked version. A conflict is reported in pip's words and gives exit 1.
- **BR-R3**: CI (`check-extras`) resolves for the runtime's platform tags with `--dry-run --ignore-installed --target <unused temporary folder>`. It writes nothing outside that temporary folder, which it removes. It succeeds only when every requirement resolves.
- **BR-R4**: pip runs with `--disable-pip-version-check --no-input --no-cache-dir`, and with `PIP_*` variables removed, so no index other than public PyPI is used and no credential is read (NFR-3).
- **BR-R5**: An absent extras file means nothing to do: exit 0 with "No requirements.txt; nothing to install." and no network access (NFR-4). A file with no requirement lines behaves the same. A path that exists but is not a regular file is a problem.

## Airflow `install_requirements` (BR-A)
- **BR-A1**: The task sits between `create_cluster` and `validate_environment` in every DAG, so `validate_environment >> submit_*` is unchanged and `stop_cluster` still follows everything (`ALL_DONE`).
- **BR-A2**: It runs `install-extras /opt/lakehouse-bundle/requirements.txt --lock /opt/lakehouse/requirements.lock` with the venv's Python in the run container, installing into that container's venv.
- **BR-A3**: After installing, the environment check with `--allow-extra` must pass (locked versions unchanged); the added packages are printed as `name==version`.
- **BR-A4**: It has 2 retries, 30 seconds apart (Q2 A). Workflow JSON can't change this; the task options apply to `submit_` tasks only.
- **BR-A5**: Its output is redacted like the other container tasks, and a non-zero exit fails the task, so no `submit_` task runs.
- **BR-A6**: The config check runs with `/opt/lakehouse/venv/bin/python`.

## CI (BR-C)
- **BR-C1**: `lakehouse-validate-workflows [ROOT]` runs the workflow rules, then, when `ROOT/requirements.txt` exists, `check-extras` against `/opt/lakehouse/workload-python/requirements.lock`. It runs both and exits 1 if either fails.
- **BR-C2**: Without `requirements.txt`, the output and exit code are as today.

## Jupyter command (BR-J)
- **BR-J1**: `lakehouse-install-requirements [PATH] [--reset]`; `PATH` defaults to `./requirements.txt`, and may be a directory, in which case its `requirements.txt` is used.
- **BR-J2**: The extras rules (BR-E) apply as in CI and Airflow.
- **BR-J3**: The folder is `~/.local/lakehouse/python3.10`. When it holds packages and its stamp differs from the SHA-256 of `/opt/lakehouse/requirements.lock`, the command refuses: "The platform lock changed since these packages were installed; rerun with --reset."
- **BR-J4**: `--reset` empties that folder (only that folder) before installing.
- **BR-J5**: Installation: a dry-run resolution against the kernel venv (which already sees the folder) lists what is missing or must change; each listed project already in the folder is first removed from it (by its `RECORD`); then exactly the listed `name==version` set is installed with `--target <folder> --no-deps --only-binary=:all:`. Locked packages are therefore never copied into the folder.
- **BR-J6**: Afterwards it writes the stamp, runs the environment check with `--allow-extra`, and prints the added packages and "Restart the kernel to use them."

## Images and parity (BR-I)
- **BR-I1**: Each image build runs `check-venv /opt/lakehouse/venv/bin/python --lock /opt/lakehouse/requirements.lock` and fails on any problem.
- **BR-I2**: The image's `/opt/lakehouse/requirements.lock` is the workspace's `infra/workload-python/requirements.lock`, byte for byte.
- **BR-I3**: The parity verifier passes only when both images pass BR-I1, both report the same Python minor version (3.10), both locks equal the workspace lock, and both `pip freeze` outputs are identical.
- **BR-I4**: The Jupyter image lists exactly one kernel spec, `python3`, display name "Lakehouse (Python 3.10)", whose interpreter is `/opt/lakehouse/venv/bin/python`.

## `generate_tpch.py` (BR-T, workload repository)
- **BR-T1**: Task arguments (after `--`): `--entity <name>` required, one of the eight TPC-H entities; `--scale-factor <sf>` optional, default `0.01`. In Jupyter (no task arguments), the notebook's `ENTITY` and `SCALE_FACTOR` variables are used (defaults `lineitem` and `0.01`).
- **BR-T2**: The scale factor is a decimal number with at most three decimal places, from 0.001 to 1. Anything else is a usage error (exit 2).
- **BR-T3**: Expected counts, computed with exact decimals: `region` 5 and `nation` 25 at any scale; `supplier` 10,000 × sf, `customer` 150,000 × sf, `part` 200,000 × sf, `partsupp` 800,000 × sf, `orders` 1,500,000 × sf; `lineitem` from 1 to 7 times the `orders` count. Verified with DuckDB 1.5.6 at 0.001, 0.01, 0.05, 0.1 and 0.37.
- **BR-T4**: It generates with `CALL dbgen(sf=<sf>)` in an in-memory DuckDB database, counts the entity (and `orders`, for `lineitem`), logs `TPC-H <entity> at scale factor <sf>: <count> rows`, and exits 1 with the expected value when the count does not match.
- **BR-T5**: `workflows/generate_tpch.json`: `schedule` null, tags `["tpch"]`, eight tasks `generate_<entity>` with `entrypoint` `generate_tpch.py` and `args` `["--entity", "<entity>"]`, no `runs_after`.
